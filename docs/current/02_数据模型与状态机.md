# 数据模型与状态机

## 1. 统一原则

- 内部 ID 为字符串 UUID，可带 PRJ/DOC/REQ 等前缀；显示编号不作为唯一键。
- 数据库存储 UTC 时间，API 使用带偏移的 ISO 8601；业务截止日期按项目 timezone（默认 Asia/Shanghai）解释。
- 后端从 deadline 与 timezone 派生 AIContext.deadline_date，不接受客户端另外提交不一致的日期；日期规则使用该派生值或要求明确指定的参考日。
- 文件字节、已引用来源块、字段及核验结果保留历史。重提取产生新产物，不能覆盖旧快照证据。
- 所有记录限定 project_id；跨项目引用必须拒绝。
- 相同操作幂等键、相同请求体返回同一资源；同键不同体返回 409。
- 修改条件、主体、负责人或有效材料后更新 input_revision；人工确认本身不递增输入版本。

旧试搭包的七表是概念起点。当前把快照、确认、补材和导出明确独立，runs 由 jobs 替代，按以下 11 张表实现。

## 2. 最小持久模型

| 表 | 关键字段及约束 |
|---|---|
| projects | id、name、context_json、scope_json、input_revision、state、current_verification_job_id、decision_json、created_at/updated_at |
| files | id、logical_file_id、version_no、replaces_file_id、source_kind、original_name、relative_path、sha256、storage_key、active_state、parse_state、current_parse_job_id、error_json；唯一 logical_file_id＋version_no |
| source_blocks | id、file_id、parse_job_id、page_index、printed_page_label、section、text、bbox_json、method、quality_json、page_image_key；来源按解析产物不可变 |
| requirements | requirement_id＋revision 为联合主键；title、category、subject_role、expected_material_types_json、conditions_json、logic_json、source_refs_json、phase、ambiguities_json、content_hash；同一 ID 的最新修订为当前版本 |
| materials | id、file_ids_json、extraction_job_id、supersedes_material_id、material_type、entity_name/person_name/product_model、facts_json、extraction_state、artifact_state、content_hash |
| snapshots | id、project_id、input_revision、context_json、requirement_versions_json、active_file_ids_json、active_material_ids_json、coverage_json、scope_json、hash、created_at；内容不可变 |
| jobs | id、kind、snapshot_id、request_key、request_hash、state、progress_json、input_json、output_json、attempt、parent_job_id、heartbeat_at、error_json、provider_run_ids_json、started_at/ended_at |
| check_results | id、job_id、snapshot_id、requirement_id/revision、check_state、condition_results_json、candidate_ids_json、evidence_refs_json、issues_json、supplement_json、dependency_hash、provider、is_simulated；输出内容不可变 |
| review_records | id、target_kind（requirement/check）、target_id、target_revision、target_content_hash、decision、note、actor_id、snapshot_id、created_at；追加记录，不覆写历史 |
| supplement_operations | id、operation（add/replace）、target_file_id、new_file_ids_json、state、job_id、base_input_revision、affected_requirement_ids_json、request_key、error_json |
| exports | id、snapshot_id、verification_job_id、kind、state、artifact_keys_json、result_bindings_json、is_simulated、created_at、error_json |

基本 JSON 结构见 `contracts/domain.schema.json`。API 类型是传输模型，ORM 可增加索引和内部字段，不得改变状态语义。

## 3. 文件与材料

files 每条对应一个不可变字节版本；同字节在同次导入重试不重复创建。相同 sha256 不可直接跨项目共享业务确认。

一个文件包含多份材料时产生多个 materials；一份材料跨多个文件时保留所有源引用。facts_json 每项有 fact_id、field_key、raw_value、normalized_value、unit、source_refs 和 extraction_state。

material_type 首批：business_license、qualification_certificate、personnel_certificate、financial_report、performance_contract、product_document、unknown。

file active_state：pending → active → superseded/disabled。parse_state：pending → processing → succeeded/partial/failed。

初次文件解析可失败，但原件仍可下载；只成功一部分页面标 partial。替换文件先 pending，只有解析和材料提取达到可用状态后才能提交切换，失败保留旧 active 版本。有 unresolved 的替换由用户处理，不自动声称替换成功。

材料重提取不改旧 facts；生成新材料产物，成功后切换 artifact_state 为 current，旧产物 superseded。旧结果仍能访问历史证据。

人工字段修订也生成新材料和新 fact ID，并用 supersedes_material_id 串联。人工原页誊写另建 manual_correction 来源块，quality_json 记录原块、操作者、时间和理由；图像页身份沿用实际原文件。它是人工修订来源，不能冒充机器原文。修订递增 input_revision，按材料变化计算重检范围。

## 4. 要求与逻辑

condition_key 在一个要求版本内唯一；保留完整 all/any 树。例如：

```json
{"all":["C01",{"any":["C02","C03"]}]}
```

C01 必须满足，C02/C03 二选一。模型提取复杂逻辑有疑问时保持待确认，不能简化成全部必需。

要求修订 API 使用 expected_revision 创建新 revision，旧版本不改。确认记录绑定确切内容 hash；修改后新版本待确认。要求原文引用同样必须属于当前项目的招标来源。

首版仅执行已支持的 operator；未知算 unknown，不随意转换为 eq。主体和阶段先处理适用性，再检查字段。资格/评分/履约阶段不得混用。

## 5. 三类状态分开

| 类别 | 状态 |
|---|---|
| 技术任务 | queued、running、succeeded、failed、interrupted、cancelled |
| 业务核验 | supported、partial、missing、contradicted、needs_review |
| 当前视图的人工状态 | pending、confirmed、stale |

人工确认不改变 check_state。用户认为提取错误时修正对应内容并重检；复核意见保留，不能靠点击确认将失败条件变为通过。

条件结果：pass/fail/unknown/not_applicable。all 内任何必要条件明确失败可导致 contradicted；any 存在有效通过路径时不因其他路径失败而判整体不符。未明确范围和处理失败会影响 missing 的可成立性。

结果归约应基于完整逻辑树及证据路径。没有材料且相关范围处理完整才可 missing；有部分支持及缺口可 partial；识别、冲突或适用性无法判断时 needs_review。来源冲突与未知不能靠总分平均抵消。

## 6. 运行快照和当前结果

核验创建 jobs 前，冻结要求版本、全部当前材料、文件处理对账、上下文和声明范围为 snapshot。AI 调用与固定检查使用该快照。

完整核验运行的 `jobs.output_json.result_bindings` 将范围内要求关联到 check_result：

```json
{"requirement_id":"REQ-001","check_id":"CHK-001","kind":"computed","dependency_hash":"example"}
```

局部重检只生成受影响要求的新 check_result；未受影响条目可绑定已有结果，kind=reused，并记录 from_job_id 与沿用依据。旧结果及 review_record 不改，新报告能追溯它原本的快照和确认时间。

整次范围与本轮重算目标分开保存：requirement_ids 是报告全范围，recheck_requirement_ids 是待重算子集。补材继承最近范围，服务端对漏选的影响项自动扩大重算目标。

沿用前必须核对：要求 revision、相关上下文字段、适用材料集合及内容 hash、证据版本、解析不确定性及相关文件对账均未改变。首版采用保守影响范围；不能可靠判断时扩大重检，不自动沿用。

只有运行完成、范围逐项对账且 snapshot.input_revision 仍适用，才原子更新 current_verification_job_id。迟到旧任务保留历史，不能刷新当前指针。

前端取 `/projects/{id}/checks` 读当前矩阵，不自行按 created_at 拼“最新结果”。输入改变而新矩阵未完成时，显示受影响项 stale，禁用对这些条目的确认及正式材料包导出。

## 7. 补材事务

1. 创建幂等 supplement_operation，检查目标文件与 base_input_revision。
2. 保存新原件，执行解析和字段提取；旧有效材料保持可用。
3. 解析失败：operation=failed，保留旧文件，记录错误，不执行后续核验。
4. 新材料可用后，短事务检查前提未变，切换有效版本并递增 input_revision。
5. affected＝旧候选/证据关联＋新旧材料类别相关要求＋相关主体＋潜在冲突项；类别未知或上下文变化时扩大。
6. 将相关当前条目标 stale，创建局部核验任务。任务用全部当前有效候选，不只新文件。
7. 输出当前矩阵；新计算结果 pending，可靠沿用的旧结果保留原复核记录。

operation 状态：pending → processing → committed → rechecking → completed。处理失败为 failed；提交后重检失败为 recheck_failed，材料切换仍保留，界面应明确还需重检。

## 8. 导出与项目决定

report 可带问题导出；reviewed_bundle 要求范围对账完成、无 stale/技术未处理、所用结果经人工确认。confirmed 的 contradicted/partial/missing 可以出现在 report；不能因此称 reviewed_bundle 内所有要求已支持。

首版 reviewed_bundle 仅为选定范围全部 supported 且确认完毕的材料包；评分缺口等其他情况用 report 导出并由人决定。报告标记 provider、is_simulated 和 scope，保留引用版本。

导出统一为 ZIP：report 包含 report.json、report.csv 和目录/问题信息；reviewed_bundle 再附原文件副本。模拟模式可以生成明确标注的演示包，不能称真实核验完成。

projects.state 可 preparing/reviewing/ready_in_scope/abandoned/archived；abandoned 由显式用户操作，保存理由。恢复需要用户明确操作并重查版本，首版可先不提供恢复按钮。

## 9. 并发与错误

- 写请求包含 expected_input_revision 或明确资源 revision；不符返回 VERSION_CONFLICT。
- 确认必须引用当前矩阵中的当前结果且依赖仍有效。
- 相同 request key 重试不重复创建文件版本、切换、确认或导出。
- 数据库事务不跨 OCR/模型网络调用；长任务靠检查点和条件提交。
- 首版同项目串行写操作，测试仍验证版本冲突；多 worker/分布式锁是后续扩展。
