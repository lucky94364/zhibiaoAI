# 智标 AI 材料核验项目团队说明

团队沟通版 2026年11月18日

我们计划参加海尔集团 AI 竞赛，围绕售前制作投标文件时的材料核验工作，开发一个 AI 辅助工作台。首版先完成“读招标要求、整理材料、逐项核验、补材重检、导出结果”这一业务闭环。本文用于团队统一目标、明确分工和安排启动工作；详细开发以 `docs/current/` 为准。

## 1 项目背景与目标

### 业务问题从哪里来

售前拿到招标文件后，需要先读懂项目背景、供应商资格等要求，再检查给定材料文件夹中的公司资质、财务资料、人员证书和业绩合同。材料常以 PDF、扫描件或图片提供，需要逐份查找、阅读和比对；发现不符合或缺失时，还要找相关人员补充，再重新核对。

与解决方案同事沟通后，我们发现：现有 AI 已能帮助编写不少标书正文，材料是否齐全、条件是否满足、依据具体在哪里，仍需要大量人工处理。因此，本项目先聚焦材料核验，后续再按实际需要扩展标书生成等能力。

### 我们要交付什么

我们要做一个能接收招标文件和材料文件夹的工作台。用户可以看到每条要求、系统找到的对应材料、原文位置、核验结论和待补充事项；补充或替换材料后，系统只重新处理变更文件，并重检受影响的要求。

系统帮助售前找到依据、识别缺口和组织材料。是否继续投标、需要补充什么以及最终是否放弃，由用户确认。材料内容支持某项要求，也不代表系统已完成证书真实性核验或确认整份投标合格。

### 用户怎样完成一次核验

1. **创建项目并上传。** 填写投标主体、项目负责人、投标截止时间和本次核验范围，上传招标文件及分类材料，保留原目录和原件。
2. **两条线路分别处理。** 招标线路提取待核对要求，由售前修订确认；材料线路识别文字、分类并提取关键字段，建立带原文出处的材料目录。
3. **汇合并逐项核验。** 对照要求、材料字段和原文证据，展示支持情况、冲突及缺口。用户可直接打开对应文件页面复核。
4. **补充或替换后重检。** 新文件处理成功后再启用新版本，重检相关要求，包括原先缺失的要求和可能产生冲突的要求，保留旧证据与历史结果。
5. **确认并导出。** 输出核验结果、匹配材料目录、内容摘录、来源索引、未解决问题及原文件副本包，供后续投标制作使用。

例如，负责人证书已过期、业绩合同未提供时，系统分别提示“材料不支持”和“未找到”。用户替换有效证书并补充合同后，系统重检相关要求，再交人工复核。

## 2 首版功能与技术路线

### 首版必须完成的功能

- **文件管理。** 支持 PDF 和 PNG/JPG，持久保存原件，生成正式编号，展示目录、版本和处理进度。DOC/DOCX 通过转换组件接入，组件不可用时明确提示。
- **招标要求提取。** 识别选定条款的核对对象、条件、证明材料、适用阶段和原文出处，区分资格、否决、评分及交付要求，支持人工修订与确认。
- **材料识别与提取。** 文字 PDF 直接提取；扫描件和图片通过 OCR 识别。先覆盖企业证照、人员证书、财务关键字段和简单业绩合同。
- **证据核验。** 展示“材料支持、部分支持、未找到、材料不支持、待人工确认”。每个结论能回到当前文件版本及原文；人工确认单独记录，不改变系统核验结论。
- **补材与局部重检。** 支持新增、明确替换和历史回看。解析失败不算材料缺失，替换失败不覆盖旧版本；旧任务不能覆盖新输入的结果。
- **结果输出。** 导出工作报告 JSON/CSV、材料目录及原件副本 ZIP，标明范围、证据及待解决事项。

### 各部分怎样配合

**前端工作台由我们自建。** 使用 React 和 TypeScript，提供项目、文件树、原文预览、要求清单、核验结果、补材及确认入口，代码位于 `frontend/`。

**业务后端由我们自建。** 使用 Python 和 FastAPI，负责文件保存、数据库、编号、版本、任务、规则检查、重检和导出，代码位于 `backend/`。运行数据放在 `var/`，不覆盖文档中的原始样本。

**文档处理由我们补齐。** 解析组件把文件转换成带页码和位置的原文；OCR 把扫描页和图片转为可检索文字，再把这些内容提供给 AI。首版采用 SQLite 和单 worker，先控制部署复杂度。

**AI 负责三类任务。** 工作流一提取招标要求，工作流二对材料分类并提取字段，工作流三完成语义核验和补材建议。日期、金额、单位等明确条件由程序检查；正式编号和业务状态也由程序管理。

集团平台的外部工作流 API 尚未确认。我们保留统一适配接口：可用时接平台工作流；直接调用内部模型也需验证实际接口。开发阶段可以显式使用 mock 模拟返回，但必须标注，不能把模拟结果当成真实 AI 接入。

### 首版边界与后续扩展

首版先用四项模拟要求跑通闭环，再扩展到公开招标样本中的 5—10 项。暂不做整本标书生成、最终投标文件页码索引、自动询价、联网验真、自动决定是否投标或复杂多 Agent。保留文件存储、解析、OCR、AI 和导出接口，后续按验证结果扩展。

## 3 八人分工与协作方式

大家按各自岗位负责规则、实现或验收。开发可由 AI 辅助完成，业务规则、专业判断和验收仍由对应成员负责。下表是建议的执行分工，启动时可根据每个人的实际时间细化。

| 成员岗位 | 主要负责内容 | 第一轮明确交付 |
|---|---|---|
| Agent 工程师 负责人 | 统筹系统设计、AI 工作流编排、接口与联调；拆分开发任务，组织人员协作和 AI 实现。 | 总体方案、三条工作流输入输出、平台接口验证清单。 |
| 算法工程师 | 文档解析、OCR、材料分类及字段来源提取，评估识别质量；知识库按需要后续建设。 | 不同文件类型的解析样例、字段与页码结果、识别失败样例。 |
| 软件工程师 | 前后端工作台、业务 API、数据库、文件持久化、任务、版本、补材重检和导出。 | 可运行工程、文件与数据链路、页面联调及部署运行说明。 |
| 解决方案 1 | 共建业务流程，收集公开招标文件，梳理要求及证明材料，定义业务测试指标。 | 首批 5—10 项候选要求、核验规则和标准答案。 |
| 解决方案 2 | 共建业务流程，组织模拟材料，独立复核结果，设计补材、替换及异常测试。 | 分类模拟材料包、正反例、完整业务验收用例。 |
| 人力同事 | 统筹可投入时间、任务安排和进度，组织系统测试；制作 PPT、演示及汇报材料。 | 成员时间表、任务与问题清单、测试计划、汇报提纲。 |
| 财务同事 | 定义财务资料的字段、期限与判断条件，制作财务反例，参与专业复核、系统测试及汇报材料。 | 财务字段和规则表、模拟财务材料、测试结论与展示内容。 |
| 法务同事 | 梳理主体、资质及证明形式等相关要求，制作反例，参与专业复核、系统测试及汇报材料。 | 主体及证明形式规则、异常材料样例、测试结论与展示内容。 |

**共同协作方式。** 售前负责说明“业务上应当怎样判断”，财务和法务补充专业条件，技术成员将规则落到系统中，再由业务成员验收。人力维护任务与问题清单，负责人协调依赖和范围；参与演示的成员共同准备 PPT 和讲解材料。

**适配业余时间。** 我们主要在工作日业余时间和周末一天投入。建议按小任务领取，每项写清负责人、输入、交付物、验收人和预计完成日；每周简短同步一次，其他进展在共享清单更新。

**业务与技术衔接。** 每条测试要求先由售前给出“原文、条件、应匹配材料、预期结论”，财务或法务复核涉及本岗位的部分，技术人员再实现。规则暂不明确时先标为待确认，避免开发 AI 自行补充判断标准。

## 4 推进安排与完成标准

### 当前进度

截至本版文档整理时，S01 工程骨架与配置、S02 数据任务及迁移基础已通过各自阶段验证，已有前后端骨架、项目接口、持久数据库和独立任务 worker。S03—S14 尚未启动，文件上传处理、OCR、AI 核验和完整业务闭环仍待实现；集团平台和真实模型尚未接入。

### 接下来怎样推进

1. **先准备业务样本并验证外部能力。** 售前确定首批要求和标准答案，财务、法务提供模拟材料及反例；负责人验证平台 API，算法验证解析与 OCR 的运行条件。人力整理任务安排。
2. **建立可靠文件链路。** 完成上传、持久保存、编号、目录、原文提取和页码预览，确保材料读得出来、原文找得到、失败能说明原因。
3. **跑通两路提取和首次核验。** 完成要求确认、材料分类、字段提取和结果对照；先用显式 mock 联调，再按已验证接口接真实 AI，并分别记录状态。
4. **完成补材及输出。** 验证证书替换、合同补充、相关要求重检、历史追溯、结果确认和导出，确保整个闭环可重复演示。
5. **做业务验收与比赛展示。** 用公开招标条款和模拟企业资料回归测试，统计错误与人工耗时，准备演示脚本、PPT、技术架构及团队贡献说明。

以上是便于全员理解的推进顺序，具体开发继续遵循当前开发文档中的 S01—S14，不另起一套开发阶段。

### 怎样判断首版做成了

- **流程跑通。** 从上传到导出使用真实业务接口，刷新页面或重启服务后仍能恢复项目和原件；真实 OCR 与 AI 接入分别有验证记录。
- **结论有依据。** 要求、字段和核验结果均能查看对应版本和原文。识别不清、条件不明确或来源缺失时不判“材料支持”。
- **补材确实生效。** 过期证书替换后相关项重检；补合同后原“未找到”项能重新判断；失败替换、重复提交和旧任务迟到不会破坏当前结果。
- **业务人员能验收。** 首批四项样本覆盖营业执照、负责人证书、财务资料和业绩合同，包含支持、过期不支持和未找到等情况，再覆盖 5—10 项公开条款。记录要求遗漏、字段错误、错误判支持、来源准确性及补材重检覆盖情况。
- **价值可以说明。** 以当前“普通 AI 加人工核对”的工作方式为比较基线，测量包含人工复核在内的总耗时。目标和结果由测试数据确定，不预设准确率或效率提升数字。

### 启动前需要对齐的事项

首先确定首批公开样本、每条要求的标准答案和可投入时间；同时核实集团工作流与模型接口、OCR 和 Word 转换的运行环境、团队使用的部署位置。人力负责确认比赛登记口径与汇报安排。这些事项未确认时，继续推进不依赖它们的任务，并明确记录限制。

本说明用于团队沟通。详细范围、架构、接口和验收以 `docs/current/README.md` 及其链接文档为准；实际开发进度以 `docs/current/progress/` 的阶段记录为准。后续需求调整先同步团队并记录，再安排实现。
